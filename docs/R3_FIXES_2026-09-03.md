# R3 감사 후 수정 및 검증

기준: `fcdb30894b12599c66ecb7984118b62fb9ccab14`의 R3 감사. 이 문서는 그 이후 로컬 수정의 개발자 검증 기록이며, 새 LIVE 독립 재심사나 운영 인증이 아니다.

## 수정 내용

| 지적 | 변경 | 검증 |
|---|---|---|
| P2-01 재측정 시 요청 단계·옛 리뷰 ID 잔류 | 증거 재오픈/재시도 때 하류의 미서명 리뷰 요청을 재오픈하고 현재 결과 ID·처리자·값을 초기화한다. 취소된 요청은 이벤트 이력에 남긴다. 화면에서 완료한 요청과 반려 후 재제출에도 새 서버 접수 ID를 연결한다. 지연 응답은 현재 pending 리뷰를 재확인한 뒤 반영한다. | SDK, 메모리/격리 PostgreSQL, 실제 로컬 UI+WebMCP |
| P2-02 단계 삭제 시 모순 조건 합성 | `qty > 10 AND qty <= 5`처럼 불가능한 범위, 경계·동등/부등·선택지 충돌을 검사한다. 삭제와 확정/HTTP 저장에서 거부한다. 다른 단계에서 다시 입력한 동일 키를 병합하는 삭제도 거부한다. 원래 규칙·노드는 변경하지 않는다. | 조건/SDK 회귀, 실제 로컬 삭제 UI |
| P2-03 재계획 승인 의미 유실 | 결정의 구조화 측정값을 설명 문장과 함께 저장한다. 서버가 저장된 현재 결정, 실제 제출값, 대상 승인 단계로 승인 범위와 경로를 계산해 리뷰 snapshot에 고정한다. `approvalPurpose: work / plan`을 작성·수정 도구와 맵에 추가했다. 카드와 완료 요약은 계획 승인과 작업 검증을 구분한다. | 서버/메모리/격리 PostgreSQL, 실제 로컬 카드·승인·재접속 |

원본 업무기록의 오래된 verification을 복사하지 않는다. 제출값이 결정의 주장보다 우선하며, 측정값에 들어온 runId/approvalStepId가 승인 귀속을 바꾸지 못한다. 기준이 없는 판단은 검사 통과로 표시하지 않는다.

기존 플레이북은 현재 결정 경로와 저장된 승인 단계의 명시적인 replan/escalation/redesign 이름이 맞으면 계획 승인으로 보수적으로 표시하며, 명시적 목적을 설정하도록 안내한다. 새 버전에는 사람에게 승인 목적을 묻고 `approvalPurpose`를 저장한다. 이미 만들어진 승인 snapshot과 과거 서명은 소급 재작성하지 않는다.

## P3 개선

- 제출용 문서에서 “unforgeable clicks”, “Zero API keys anywhere”, 모든 수정이 LIVE 검증됐다는 표현을 정리했다. 사이트 소유 LLM 키 불필요, 서버 역할/증거 검사, LIVE/LOCAL 범위를 구분했다. 실제 Devpost 제출 폼은 수정하지 않았다.
- snapshot 없는 과거 이력은 기존 결과가 유지됨을 설명하고, pending 리뷰의 재요청 안내와 구분했다.
- 작은 화면에 탭 스와이프 안내와 하단 safe-area 여백을 추가했다. 타임라인은 최근 6개를 먼저 표시하며 전체 펼치기와 읽기 쉬운 글자 크기를 제공한다.
- 처음 열 때 실행 복원 중 상태를 표시한다. 실패 시 재시도를 제공하며 기존 실행 대신 새 실행을 조용히 만들지 않는다.

### 실제 로컬 UI + 공개 WebMCP

프로덕션 빌드를 별도 메모리 서버 `http://localhost:18996/`에서 열었다. 합성 업무로 진행했으며 LIVE 감사 데이터는 변경하지 않았다.

1. 실행 #2: 12/false 입력→요청 #4→측정 단계만 재오픈. 화면에서 측정 READY, 요청 PENDING, SKIPPED 없음, 현재 produced IDs 없음 확인. #4는 CANCELLED이며 원래 12/false snapshot 유지.
2. 실행 #2: 3/false 새 입력→공개 `request_review`를 사람 확인 카드로 실행→새 요청 #5. Lee 반려→Kim 재제출 #6→Lee 승인. 새로고침 후 요청 단계와 승인 단계 모두 resultId #6, 3/3 완료 확인.
3. 실행 #8: 실제 12/false→실패 분기→`schemaRedesignNeeded:true` 결정→리뷰 #10. 카드에서 12/false·redesign true, “Replanning approval — approves the plan only. Work validation remains failed.” 확인. 판단 근거 두 개를 펼쳐 확인하고 계획만 승인. 새로고침 후 2/2 완료와 동일 경고·값 유지.
4. 편집 초안: 같은 qty를 두 번 측정하는 중간 단계 삭제를 거부하고 세 노드가 유지됨을 확인. 두 번째 입력 바인딩을 제거한 경우에도 `qty > 10 AND qty <= 5` 합성 삭제를 거부하고 원래 조건을 보존함을 확인.

브라우저 확인은 데스크톱에서 수행했다. 모바일 CSS 개선은 이번 라운드에서 물리 기기나 375px 브라우저로 다시 검증하지 않았다. 반복 요청/응답 손실 및 DB 검사는 로컬 자동검사 범위다.

## 인계

이 검증은 로컬 수정본을 대상으로 했으며 LIVE 배포 결과는 포함하지 않는다. 새 빌드를 배포한 뒤 LIVE에서 위 네 시나리오와 기존 정상·복구·중간 승인 경로를 다시 확인하면 된다. 감사의 기존 리뷰·실행·증거 기록을 청소하거나 덮어쓰지 않았다.
