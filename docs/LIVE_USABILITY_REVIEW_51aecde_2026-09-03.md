사용자가 설명한 서비스 가치에 동의한다. 이번 검증에서 가장 좋은 장면은 실패값을 거부하는 장면만이 아니었다. **한 업무 문장이 사람의 답을 거쳐 프로세스가 되고, 다음 업무에서 그 프로세스가 추천되어 새로운 담당자 작업으로 시작되는 장면**이 제품 정체성을 가장 잘 드러냈다.

반면 “승인 후 생산 인계”라는 자연스러운 사용자 답을 그대로 구조화했을 때 실행이 막혔다. 심사자의 관점에서는 준비된 예제의 성공보다 이러한 일반화 실패가 더 중요하다. 사용자가 말한 앞뒤 업무를 자유롭게 받아들일 수 있어야 제품의 약속과 구현이 일치한다.

이전 로컬 심사 82점과 이번 78점은 동일 조건의 전후 실험이 아니다. 이번에는 배포판에서 승인 뒤 후속 업무와 탭 이동·새로고침·개정 비교까지 범위를 넓혔다.

**수정 방향:** 현재 승인 단계와 활성 경로에서 필요한 선행 업무를 기준으로 서버 관문을 계산하고, 승인 후 후속 단계는 실행 가능한 다음 업무로 남겨야 한다. 승인 주체를 run 전체뿐 아니라 승인 단계에도 연결할 필요가 있다. 기존의 미완료 선행 업무·실패 증거 차단은 유지해야 한다.

**재검 기준:** `준비 → 검토 → 승인 → 인계`에서 검토를 마치면 요청 1건 생성, 승인 후 인계만 READY, 인계 전에는 run 미완료, 인계 완료 후 completed. 미완료 선행 업무가 있는 요청은 계속 거부해야 한다.

## 그래픽과 이력 화면의 추가 관찰

- **오른쪽 그래픽은 삭제되지 않았다.** 생성·편집·실행·개정 동안 표시됐고 현재 단계, 담당 역할, 실패·성공 분기와 재작업 루프가 보였다.
- 데스크톱에서도 패널은 최대 360px(`sdk/panel.ts:36`)이고 상단 미니 그래프는 번호 위주다. 실행 화면의 넓은 빈 공간에 비해 절차 설명과 분기 문구가 오른쪽에 밀집한다. 패널 너비 조정 또는 큰 프로세스 보기로 전체 흐름을 읽는 부담을 줄일 수 있다. 표시 오류로 단정하기보다 가독성 개선 사항이다.
- v2 선택 시 실행 이력은 `Not run yet.`이고 목록에는 최신 버전만 나타났다. “1 earlier version(s) in history” 안내는 있지만 해당 화면에서 v1 실행 #15·#16으로 직접 들어가는 선택지는 보이지 않았다. 데이터 삭제는 확인되지 않았으며, 버전 간 실행 이력 탐색의 발견 가능성이 낮다는 관찰이다.

## 재현 자료와 운영 데이터 영향

이번에 만든 자료만 `QA-LIVE51`로 구분했다. 기존 시연 플레이북 #53과 기존 검토 요청 #1을 수정·승인하지 않았으며, 데이터 전체 초기화는 하지 않았다.

| 자료 | ID | 검사 종료 시 상태 |
|---|---|---|
| 업무 입력 | worklog #16 | 합성 출발 업무, draft |
| 승인 후 인계 재현용 플레이북 | process #70 v1 | 6단계 구조 보존 |
| 교착 실행 | run #14 / worklog #17 | 비교 실행 시작 시 서비스의 단일 활성 실행 정책에 의해 abandoned; 검토 기록은 draft |
| 마지막 승인 비교 플레이북 | process #71 v1 | 원본 비교 버전 보존 |
| 비교 실행 | run #15 / worklog #18 / review #17 | completed / approved / APPROVED |
| 추천을 통한 재사용 | run #16 / worklog #19 / review #18 | completed / approved / APPROVED |
| 경험 반영 버전 | process #72 v2, sourceProcessId #71 | 정렬 확인 절차 설명 저장, 아직 실행하지 않음 |

worklog는 15→19개, review는 16→18개가 됐다. 플레이북은 제목 2종, 저장 버전 3개를 추가했다. 감사 자료를 남겼으므로 이후 시연 준비 때 `QA-LIVE51` 범위를 식별할 수 있다.

## 검증의 한계와 다음 수정 순서

실제 직원의 서로 다른 로그인·동시 접속, 네트워크 단절·장기 부하, 키보드·스크린리더 전체 접근성, 일반 사용자의 독립 완주율, 동의어·여러 언어를 포함한 추천 품질은 이번에 검증하지 않았다. 본문에서 입증한 역할 인계는 judge 로그인 내 데모 페르소나 전환이다. 실운영 권한 분리의 증명으로 사용하면 안 된다.

수정 순서는 **중간 승인 관문과 오류 표시 → 문제·재시도 이력 보존 → 작성 문맥 보존 → 지식 변경 비교 → 첫 화면·그래프 가독성**이 적절하다. 수정 뒤에는 특히 기존 실패 증거 차단을 유지한 채 `승인 → 인계`가 끝나는지 동일 라이브 시나리오로 재검해야 한다.
