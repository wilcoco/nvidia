# 업무 발견·실행·재사용 개선 계획

대상은 라이브 51aecde 심사에서 재현한 L1–L7이다. 업무 입력, 질문과 사람의 교정, 역할별 실행, 재사용, 경험을 반영한 개정의 순환을 유지한다. 데스크톱 입력과 오른쪽 프로세스 그래픽을 기본 경험으로 삼는다.

## 구현 범위와 완료 기준

1. 승인을 개별 단계에 연결한다. 서버는 해당 단계의 선행 업무와 미해결 결정을 검사한다. 후속 인계를 선완료 요구하지 않는다. 여러 승인에서도 각각의 증거와 검토 요청을 구분한다.
2. 검토 요청 중·완료·실패를 명시하고 일시적 동기화 지연만 제한적으로 재시도한다. 실패에는 원인과 재시도 버튼이 있다.
3. 문제 보고와 작업 시도를 실행 이벤트로 영속화한다. 재시도 때 현재 증거는 초기화하되 이전 시도는 이력에 보존한다. 새 버전과 새 실행에는 옛 실행 이력을 복사하지 않는다.
4. 업무 입력 초안과 추천 문맥을 탭 이동·새로고침에서 보존한다. 새 로그인은 업무 입력부터 시작하고, 이전 실행은 명시적으로 선택한다.
5. 첫 화면 설명을 줄여 입력·시작을 위로 올린다. 오른쪽 프로세스 패널은 유지하고 넓게 볼 수 있게 한다.
6. 설명·판단 기준·연결·입력 정의 변경을 버전 비교에 표시한다. 이전 버전을 선택해 그 실행 이력과 문제를 볼 수 있다. 문제에서 개정 초안을 시작할 수 있다.

## 검증

- 서버: 선행 업무 미완료 차단, 중간 승인 후 인계, 연속 승인 구분, 증거 변경 시 이전 검토 무효화.
- 저장소: 메모리 및 가능한 격리 PostgreSQL에서 단계별 검토와 이벤트 누적·재조회.
- SDK: 재작업 후 최신 증거만 판정에 사용, 이전 이벤트 보존, 복원, 새 실행·개정 상태 분리.
- 브라우저: 데스크톱 업무 입력 → 질문·교정 → 저장 → 실패·재작업 → 중간 승인 → 후속 인계 → 완료 → 추천·재사용, 입력 보존·버전 비교.
- 라이브 데이터는 합성 QA만 사용한다. 앱 배포 여부와 로컬 검증 결과를 구분해 기록한다.

## 완료한 검증

- `npm run check`, `npm run build`, `git diff --check` 통과.
- `TEST_DATABASE_URL=postgresql://127.0.0.1:56439/understudy_improve npm test`: **25개 통과**, 메모리와 격리 PostgreSQL의 HTTP/저장소 검사를 포함한다.
- 기존 실패값 거부, 재작업 재개, 낡은 승인 무효화, 다른 로그인에서 승인, 동시 요청 중복 방지 검사를 유지했다.
- 중간 승인 뒤 인계와 두 번째 승인, 승인된 선행 증거 변경 차단, 이벤트 영속화, 설명·연결 변경 비교, 입력 복원, 영구 검토 실패의 표시·수동 재시도를 추가 검증했다.
- PostgreSQL JSONB의 키 순서와 브라우저 JSON 키 순서 차이로 동일 증거가 바뀐 것으로 판단되는 문제를 브라우저 재사용 검사 중 발견해 수정했다. 정규화된 비교와 기존 배포판 지문 형식의 호환성도 검사했다.

## 실제 브라우저 E2E

[개선 버전 미리보기](http://localhost:18990/)는 별도 PostgreSQL `understudy_browser`를 사용한다. 기존 라이브 데이터는 이번 코딩·검증에서 변경하지 않았다.

1. 업무 문장 작성 → Work log 왕복 → 새로고침: 문장과 문맥 유지.
2. 질문 카드 응답 → 7단계 맵 구성 → 사람이 측정 단계 이름 교정 → v1 저장.
3. Park 준비 → Kim 실측 3 → 에이전트가 주장한 0 거부 → 재작업 분기.
4. Park 문제 보고 → 바로 새로고침 → 문제·기존 증거 복원. 조정 기록 후 재측정 0.
5. 중간 리뷰 생성·Lee 승인 → Park 인계 입력 → 별도 최종 리뷰·Lee 승인 → run #1 완료.
6. 실행 이력의 문제 보고 선택 → 개정 초안 → 정렬 확인 절차를 설명에 추가 → v2 저장·설명 변경 비교 확인. 버전 선택으로 v1 run #1 이력 접근.
7. 로그아웃/로그인 → 자동 완료 화면 대신 입력 화면. 다음 금형 업무에 v2 추천 → 새 run #2, 빈 입력과 개선 지침 확인.
8. run #2의 중간 승인 뒤 JSONB 비교 오류를 발견·수정. **Retry saving progress → Retry review request**로 상태를 복구한 뒤 인계·최종 승인 완료. 새로고침 후 완료 및 중복 없는 승인 2건 복원.
9. 이전 실행 선택으로 run #2 재열기와 오른쪽 그래픽 확대 확인. 최종 새로고침 세션의 브라우저 warning/error 로그 없음.

로컬 QA 자료는 process #1(v1), #2(v2), run #1·#2, review #1–#4다. 첫 실행의 초기 구현에서 중복 기록된 승인 이벤트는 그 로컬 QA 이력에 남아 있지만, 마지막 구현으로 생성한 run #2는 승인별 이벤트가 1개씩 보존된다.

## 운영 반영 시 참고

- DB 변경은 `approvals.step_id`, `approvals.review_scope`, `process_runs.events` 추가이며 시작 시 적용된다. 기존 기록은 기본값으로 읽고, 이전 검토 지문도 값이 같으면 호환된다.
- 이벤트가 없던 과거 실행의 상세 작업 이력을 소급 생성하지 않는다.
- 승인 선행 범위는 현재 SDK의 순서 있는 단계·분기 실행 모델과 일치시켰다. 임의 병렬 DAG 엔진으로 바꾼 것은 아니다.
- 실제 고객 사용성 연구, 장시간 부하와 다중 브라우저 동시 작업 전체는 이번 범위에 포함하지 않았다. 라이브 배포 후 동일 흐름의 재검이 필요하다.
- 로컬 미리보기 서버는 18990, PostgreSQL은 56439에서 실행 중이다. 임시 클러스터 경로는 `/tmp/understudy-improve-pg.gtOstV/data`. 미리보기를 계속 사용할 수 있도록 유지했다.
