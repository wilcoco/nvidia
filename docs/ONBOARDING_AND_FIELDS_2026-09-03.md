# 업무 발견·입력 양식·분기·협업 갱신 검증 (2026-09-03)

## 구현

### 첫 진입과 질문

첫 화면은 업무 입력과 새 프로세스 작성/기존 프로세스 재사용을 중심으로 안내한다. 업무를 저장하면 선행 업무에 관한 첫 질문이 바로 나타난다. 답은 해당 업무 기록의 `data.discovery.before`에 저장되고 새로고침 뒤에도 에이전트가 읽을 수 있다. 아직 저장하지 못한 답은 세션 초안으로 유지된다. 복사 버튼은 에이전트에게 보낼 문장을 제공하며, 복사만으로 대화가 실행된다고 표시하지 않는다.

`describe_workspace`에 `show_guide`, `guide_language`, `guide_topic`을 추가했다. 소개 의도에는 overview, 사용 방법에는 usage 안내를 웹 패널에 표시한다. 한국어/영어를 지원하며 기존 초안이나 입력 중인 편집기는 유지한다. 질문 문구의 의미 해석은 방문자의 호환 WebMCP 에이전트가 담당한다. 특정 문장만 매칭하는 사이트 내 챗봇은 아니며 모든 에이전트의 모든 표현을 자동 보장한다는 주장은 하지 않는다.

### 단계별 입력 양식

- `FieldDef.type`에 `select`와 `options: string[]`를 추가했다. 선택지는 중복 없는 비어 있지 않은 문자열이어야 한다.
- 단계별 인터뷰 의제에서 수치/단위, 유지할 값, 선택지, 필수 여부, 기록 담당자·단계, 판단 기준과 선택별 후속 업무를 묻도록 안내한다.
- 모든 입력 키는 실제 입력 가능한 task의 `fields`에 연결해야 확정·저장할 수 있다. 정의만 하고 담당 단계에 연결하지 않아 양식에서 사라지는 경우를 차단한다.
- 오른쪽 초안/실행 패널에 각 담당 단계의 입력 항목·단위·선택지·필수 여부를 표시한다.
- My tasks에서 담당자는 숫자와 드롭다운을 입력한다. 드롭다운은 자동으로 첫 값을 선택하지 않는다. 필수값이 없으면 완료 버튼이 비활성화된다.
- `shared/fields.js`를 SDK 엔진과 HTTP 저장 경계에서 공유한다. 미입력, 숫자로 위장한 문자열, NaN/Infinity, 미정의 선택값을 거부한다. 숫자 0과 boolean false는 유효한 측정값이다.
- 수치 입력의 유효성과 통과 기준은 구분한다. 예를 들어 숫자를 기록했다는 사실만으로 승인 조건을 통과한 것은 아니다.

### 드롭다운 분기

선택이 경로를 결정할 때는 사람에게 각 선택의 후속 작업을 묻고, 결정 간선에 `criteria: {shippingMethod: {eq: 'Courier'}}` 같은 조건을 저장한다. 문장으로 적은 설명만으로 선택값을 강제한다고 보지 않는다. 알려진 select 필드의 분기 조건은 허용된 선택값을 사용해야 한다.

담당자의 실제 제출값을 기준으로 `resolve_decision`이 경로를 확인한다. 다른 선택으로 주장하거나 맞지 않는 간선을 요청하면 거부한다. 모바일에서는 값을 제출하고, 분기 처리는 데스크톱 WebMCP 에이전트가 수행한다.

### 다른 탭에서 결재한 뒤의 갱신

기존 폴링은 업무일지·결재 목록만 읽었고 현재 열린 SDK 실행은 갱신하지 않았다. 이제 현재 run을 인증된 GET API로 읽어 기존 맵 객체에 실행 상태를 적용한다. 주기적 갱신과 창 복귀 시 갱신을 사용하며 전체 페이지 재로딩은 필요하지 않다.

서버 읽기를 시작한 뒤 로컬 작업이 바뀌거나, 저장 중이거나, 다른 run/초안으로 전환되면 늦은 응답을 적용하지 않는다. 원격 상태 적용 자체는 쓰기 동기화를 다시 발생시키지 않는다. My tasks의 입력 초안은 동일 run 내 갱신에서 유지된다. 기존의 인증 세션 기반 run 쓰기 소유권은 유지하며, 이번 수정이 일반적인 다계정 공동 편집 권한 체계를 새로 구현한 것은 아니다.

추가로, 단계 편집기의 blur가 저장 버튼을 클릭하기 전에 패널을 다시 그려 첫 클릭을 잃는 문제를 보완했다. 버튼의 클릭 처리가 끝날 때까지 해당 DOM을 유지한다.

### 실제 UI + 등록된 WebMCP 도구

검증자가 만든 로컬 QA 자료다. 실제 고객 도입 사례나 사용자 인터뷰 결과가 아니다.

1. `QA-INTRO` 업무 #6에서 선행 업무 답을 저장했다. 탭 이동·새로고침 후 같은 답을 화면 및 `describe_workspace`로 확인했다. 실제 추가 질문 카드 응답을 도구로 읽어 초안을 만들었다.
2. 한국어 서비스 소개와 사용법 안내가 웹에 나타났다. 일반 `describe_workspace` 호출은 안내를 임의로 열지 않았다. 편집 도중 도움말을 열어도 맵 JSON과 입력 중인 문장이 유지됐다.
3. 업무 #6을 출발점으로 `QA-INTRO · Customer delivery` v2(process #4)를 확정했다. Park의 단계에는 Package weight(kg), Delivery method(Courier/Pickup), Kim의 마지막 단계에는 Receipt reference를 연결했다.
4. Run #3: Kim의 주문 확인 → Park의 양식 표시. 무게만 입력한 상태에서 필수 선택이 없어 완료가 잠겼다. **12.5kg + Pickup**을 제출했다.
5. Courier 분기 요청은 `shippingMethod must equal Courier (got Pickup)`로 거부됐다. Pickup 분기에서는 **Send collection notice**가 Kim의 업무로 나타났고 Courier 업무는 N/A였다.
6. Kim이 수령 안내를 끝내자 결재 요청이 생성됐다. 별도 브라우저 탭의 Lee는 12.5/Pickup 증거를 확인하고 승인했다. 원래 Kim 탭은 페이지 새로고침 없이 **4/5 완료 + Confirm receipt 입력 양식**으로 바뀌었다.
7. Kim은 `QA-PICKUP-2026-09-03`을 입력했다. 폴링 이후에도 같은 값으로 제출됐고 **5/5 완료**했다. 새로고침 뒤에도 run #3, Pickup 분기, Lee 결재, 최종 입력값이 복원됐다.
8. 편집 후 저장의 한 번 클릭을 최신 패널 코드로 재검증했다. v3(process #5)에 변경 문장이 정상 저장됐다.

10. 검증 중 브라우저 경고·오류 로그는 없었다.

## 드롭다운 시연 순서

1. 업무 작성 중 “이 단계에서 기록할 무게와 배송 방식은? 각 방식 다음에는 누가 무엇을 하나요?”라는 질문에 답한다.
2. 오른쪽 초안에서 Park의 숫자/드롭다운 양식과 Courier/Pickup 두 갈래를 보여주고 확정한다.
3. 실행에서 Park가 무게와 Pickup을 제출한다. 선택값과 다른 Courier 요청이 거부되는 모습을 보여준다.
4. 데스크톱 에이전트가 제출값으로 Pickup 경로를 진행하면 Kim의 수령 안내가 나타난다.
5. 다른 탭에서 Lee가 승인하고, 원래 Kim 화면에 마지막 수령 확인이 나타나는 장면으로 연결한다.
6. 새 업무에서 같은 플레이북을 선택하고 이번에는 Courier로 진행한다. 저장한 경험이 다른 선택값에 따라 다른 업무를 배정하는 재사용 장면이다.
