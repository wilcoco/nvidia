## 자동 리뷰 장애 복구

기존 모형 검증을 실제 로컬 Express 서버와 메모리·PostgreSQL DB로 넓혔다. 앱의 실제 `autoSyncApproval`과 API 코드를 사용하고 전송 계층에서 응답 유실을 제어한다.

- 승인 지점 3종: 정상 결과, 복구 후 결과, 재계획 결과를 담은 승인 준비 fixture.
- 각 지점별 5조건: 정상, 일지 생성 전 실패, 일지 생성 후 응답 유실, 리뷰 제출 전 실패, 리뷰 제출 후 응답 유실.
- 백엔드 2종 × 승인 지점 3종 × 조건 5종 = **30조건**.
- 각 조건에서 동시 8회·추가 20회 자동 리뷰 호출 후 **기록 1개·pending 리뷰 1개**로 수렴했다.
- 응답 유실 후 첫 상태 조회도 실패시키므로 단순 성공 응답 처리만 검사한 것이 아니다. 실제 재시도 간격을 사용했다.
- 합성 리뷰 기록 생성은 `runId + approvalStepId` 기준으로 중복 방지하며, PostgreSQL에서는 실행 행 잠금 안에서 조회·생성을 처리한다.
- 서버 반영 뒤 응답이 유실된 경우에도 조회로 성공을 확인하면 Activity에 복구 확인 문구를 남긴다.

이 테스트의 정상/복구/재계획은 **승인 지점의 준비된 fixture**다. 세 전체 업무 경로를 브라우저에서 장애 주입하며 완주했다는 뜻이 아니다. 배포 서버의 네트워크 장애 주입도 하지 않았다.

## 브라우저 증거

검증 환경: Codex 내장 브라우저, `http://localhost:18991/`, 격리 PostgreSQL `understudy_browser`. 기본 데스크톱 크기는 940×994였고, 모바일 점검에만 375×812를 적용한 뒤 복원했다.

1. `QA-AUDIT · Repeated quality checks` v1(#6) → v2(#7), dry 기준 10 → 12 저장 후 실행 #5를 시작했다.
2. 작업형 복구를 3회 반복했다. 이전 완료로 다음 회차를 건너뛰지 못하고, 성공값을 주장해도 실제 실패 제출이 우선했다.
3. `0/true` 리뷰 대기 후 업무를 다시 열었다. 두 탭 경합을 추가 발견하여 고친 뒤 같은 경로를 재검했다. 리뷰 #7은 취소됐고 `12/false`가 현재 증거로 남았다. 최초 경합 재현에서 생성된 #6도 취소 상태로 보존했다.
4. 실제 복구·dry 15·새 `0/true` 제출로 리뷰 #8을 만들었다. Lee가 다른 탭에서 승인하자 원래 탭에 새로고침 없이 #5 완료(2/2)가 반영됐다. 완료 후 `resolve_deviation`은 거부됐다.
5. 완료 #5에서 새 `QA-AUDIT · Handoff isolation`을 저장했다. 저장본은 라이브러리 #8(v1), #9(v2)이며 명시적 Run으로 #6을 시작했다. Kim의 참조번호 → Park의 수량 4 → Lee의 별도 리뷰 #9 승인으로 3/3 완료했다.
6. 이전 완료 #3과 #5의 전체 DB 행(단계·결과·처리자·시각·판단·이벤트·상태·updated_at 포함)이 새 설계 저장·실행·승인 후에도 동일했다.
7. 설정의 새 업무 시작을 2회 확인 클릭으로 실행해 빈 업무 입력으로 돌아왔다. 저장된 QA 자료는 남겨 두었다.

QA 자료는 합성 데이터다. 역할 전환은 데모 페르소나이며 실제 사용자 연구나 독립 심사위원의 평가가 아니다.
